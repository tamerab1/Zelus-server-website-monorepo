# Rev 231 -> 241 migration tooling (branch `upgrade-rev-241`)

These tools only read caches. They compile against `.dev/cache-restore-tool/fatjar` (plus `SpliceItemOption.java` from `.dev/cache-restore-tool/src`). Run them with the classpath in `cp_with_jna.txt`; vanilla 231 builds need JNA for bzip2.

Inputs live outside the repo in `osrs server/archive/rev241/` (OpenRS2 caches 2746 = rev 241 and 2247 = rev 231, plus keys and SHA256SUMS). The branch server reads the isolated `osrs server/data zelus rev241/`.

- `spikeA/MapCodec.java`: terrain + loc codec. 241 terrain = 231 tile grammar, then a u8 count of extra 64x64 layers. 241 locs = 231 grammar, no XTEA. Index 5 group = regionId; files 0 terrain, 1 locs, 2 environment preset, 3 = [0,0], 4 = [0].
- `spikeA/FinalCheck.java`: the go/no-go proof. Byte round-trips all vanilla 241 + 231 regions, checks against RuneLite's MapLoader, and converts every local region.
- `spikeB/ModelBudget.java`: custom model census, dedupe, and slot budget under 65535.
- `assessment/`: id-collision census, base-build match, and semantic def/model diffs.

## Id remap (`remap/`)
- `BuildRemapManifest.java` -> `remap-241.json`. For each id type it lists our custom ids that collide with vanilla 241 and where each one moves. Rules: a constant shift above 241max + 2x the 231->241 growth wherever it fits (this keeps arithmetic between custom ids, e.g. bond tiers / placeholder +100). Where it doesn't fit (models, objects under 65535), the ids are packed against the limit. Models with the same bytes as a vanilla 241 model reuse it. Varps include "phantom" varps (varbit base varps with no varp definition: 4829-4836). Every target is validated as free, unique and <= limit.
- 16 id types. New vs the first census: sound effects (145, all colliding), clientscripts (57), textures (86), overlay/inv/config18 (1 each), phantom varps (8).
- The cache build must ADD varp definitions up to the new varp ids: the 241 client sizes its varp arrays from the defined varps.

## Save migration (`saves/`)
- `save_migration_dryrun.py <manifest> <data> <report.md> [rules.json] [dumpDir|-] [varbit-moves-231-241.json]`: read-only census + simulated remap; writes only the report (and optional copies to dumpDir). With the moves file it also re-packs raw saved varps for the ~1206 vanilla varbits that moved between 231 and 241 (regenerate with `cache/VarbitMoves.java <our231 cache> <cache241> <out.json>`). **Always pass it for real 231 saves**; never run it on saves already played on 241. Local 231 data (2026-10-27): 34 files re-packed, 37 values moved, 4 dropped (varbits 4371/4372 shrank to 1 bit), 0 slots changed outside the moved varps. Dump to a short path (e.g. `C:/z241relay`): the scratchpad overruns MAX_PATH.
- `rules.json`: path classification, each rule checked against the server code. Special kinds: `varp-index-array` (Player.varps is indexed by varp id: values move slots, the old slot is cleared, the destination must be empty) and `packed-var-key` (savedConfigs keys = id << 16 | isVarbit).
- `dryrun-local-20261025.md`: local dev data verdict READY (1108 files, 532 item fields, 0 violations, 6 NUL-filled orphan files passed through). Synthetic tests of the varp / packed-key / item-key transforms all pass, and the "destination not empty" violation is caught.

## Static data remap (`data/`)
- `remap_data.py <manifest> rules.json <data> <report.md> [--apply]`: remaps ids in the server's static data (drops, spawns, combat, shops, item_info, pets, deals, weapon/shield types, teleport previews) and renames id-named files (`npcs/drops/newDrops/<npc>.json`, `item_icons/<item>.png`). It leaves `runtime/`, `saves/` and `gear_loadouts/` to the save migration, and skips caches, vanilla dumps and `*backup*` dirs. Dry run by default.
- The files are lenient Gson JSON (`#`, `//` and `/* */` comments, unquoted keys), so strict parsers fail. `lenjson.py` tokenizes them and numbers are patched in place by byte span, which leaves comments, spacing and CRLF untouched. Shop YAML is patched line by line under `defaultStock:`.
- `--apply` writes the marker `.rev241-data-remapped` and refuses to run twice. The model map has a chain, so a second pass would not be a no-op.
- The report lists "unruled" numbers: a moving old id at an id-looking key with no rule. Every one must be explained before cutover.
- Verified 2026-10-25 on a copy of the local data: 658 replacements in 39 files, 468 renames, 0 unruled. Every change is a mapped number (non-numeric bytes identical), and a second dry run finds nothing left to move.

## Java/Kotlin literal remap (`java/`)
- `remap_java.py <manifest> decisions.tsv <repoRoot> <report.md> [--apply]` rewrites int literals that equal a moving old id. The same number means different things in different places: 60010 is a custom item (stays, since 241 items end at 34731) and also a custom object (moves). So each literal carries a reviewed semantic type in `decisions.tsv` (or `none`: coordinate, amount, colour, region) and only moves when that type moves it. Decisions match on file + value + occurrence + code text, so line shifts don't break them. `--apply` refuses while any literal has no decision. In `cache/ItemID|NpcID|ObjectID` (vanilla dumps) the file decides the type.
- `review/`: how `decisions.tsv` was produced. `java_census.py` finds the hits. `java_classify3.py` types them by parameter name at the argument position (signature index over all sources, plus a curated `PARAM` map), then `x.getId() ==` receivers, call names, assignment names and 231-cache existence (`../cache/DumpIds.java`). `build_decisions.py` adds the hand-reviewed overrides. Line-keyword guesses proved unreliable (e.g. `SLOT_CHEST` read as an object) and every one was reviewed.
- Applied 2026-10-25 to the branch: 139 files, 872 literals moved (item 650, spotanim 107, npc 43, obj 34, seq 14, model 10, varbit 8, clientscript 6), 1882 kept, every change digits-only. After merging new develop code, re-run: new hits show up as unresolved.
- Traps found in review: FortuneInterface's `{model, 16203}` pairs are idle seqs (don't move), though 16203 is also a moving npc. `33000 + logId` in PerkTasks/Burning is a perk key, not an item. GroundItem's `id < 32768` proxy path is harmless on 241: the 241 client no longer masks ground item ids to 15 bits (verified in the injected client bytecode), and the proxies move with their items.

## Interface components (`remap/`, `cache/AlignOurs231`, `java/iface_*`)
- Jagex renumbered components in 141 vanilla interfaces between 231 and 241. `remap/component_map.py` builds the 231 -> 241 map from RuneLite's gameval `InterfaceID` names (`remap/gameval/`: upstream 6c3642d7d = 2025-07-23, last rev 231 update, matches OpenRS2 2247 in all 924 groups; 009555a90 = 2026-10-20 = OpenRS2 2746). Do NOT use the client fork's own `InterfaceID.java`: it is older than 231 for some groups (229).
- `cache/AlignOurs231` aligns OUR live cache's components with vanilla 231 per edited group: "overwritten" = a Zelus interface under a vanilla id (24 groups incl. 119/873/879); "aligned" = a vanilla group with a few edits. Our 218 lacks vanilla 193, so ours 193-202 = vanilla 194-203 (override in the tool).
- Stage 4 places each of our edits at the 241 position of the vanilla component it edits. Before this fix it matched by id, which put the spellbook's "Previous" option on Minigame/Zaros teleports and our Lunar home over an Ancient spell. Every component reference inside our components (parents, hook args) and ICONSTs in our scripts (stage 5) go through the same operator (`BuildInterfaces241.loadRefs`).
- `remap/effective_component_map.py` -> `component-map-effective.json`: what the SERVER must follow, from our layout to cache241's (alignment, then Jagex's renumbering, then stage 4's moves).
- `java/iface_census.py` finds every server site addressing a renumbered group (calls with (group, comp) arguments, `h.actions[c]` in register blocks, `g << 16 | c`, packed literals). `java/iface_remap.py` rewrote the plain literals (110). The rest were hand edits. `iface-sites-applied.tsv` is the census the remap ran on.
- `java/rekey_decisions.py` re-keys `decisions.tsv` to the current code, so `remap_java.py` stays re-runnable after apply.
